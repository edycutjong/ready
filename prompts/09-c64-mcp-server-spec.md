## What the feature is
A stdio MCP server named `c64` at `mcp/c64-server/server.ts` (run as `node mcp/c64-server/server.ts`; Node ≥ 22.18 strips types; ESM, `.ts` import suffixes; deps already installed: `@modelcontextprotocol/sdk` 1.32.2 and `zod` 4). It is the Kiro `resurrector` agent's ONLY way to touch a real Commodore 64 (the headless c64-ready core via `src/emu/node.ts` → `bootNodeCore()`). Keep the tool logic in a pure-ish module `mcp/c64-server/tools.ts` (a class or factory taking a `C64Core` and a run-dir path) so tests can drive every tool without stdio; `server.ts` only wires the SDK, zod schemas and stdio.

## Run directory contract (every file lives in `$RUN_DIR`, an env var; the server refuses to start without it)
- `input.json` — written by the runner BEFORE the session: `{ listingId, scope, spec: ListingSpec, lines: CanonicalLine[], provisional: number[] }` (`ListingSpec` from `src/emu/session.ts`; `provisional` = line numbers restored by recovery code, not yet proven by a run).
- `listing.json` — owned by the server. Written at start, after every accepted/forced patch, and after every run: `{ listingId, scope, expectedLines, lines: (CanonicalLine & { provisional: boolean })[], hash, untypeable, iteration, postTitle, contract }` where `hash` = sha256 hex of the canonical text (lines sorted by number, `n + " " + body` joined by "\n"), `untypeable` = `untypeableLines()` result, `iteration` = count of apply_patch calls the server received, `postTitle` = "pass" | "fail" | "not-reached" from the last run, and `contract` = `{ state: Verdict, scope, heading, counts, failed, lines: {n, status, source, provisional}[] }` computed with `judge()` from `src/emu/session.ts` after each run (before any run: state "NOT-RESURRECTED", heading from `evaluate` with titleSeen false).
- `state.json` — owned by the server, written after every `c64_run` / `c64_read_screen` / `c64_press`: `{ iteration, screen, error: {kind, line} | null, titleSeen, postTitle, at }`.
- `events.jsonl` — append-only, one JSON object per line, `{ t: ISO time, k, ... }`: `{k:"emu", op:"load", hash, untypeable}`, `{k:"emu", op:"run", error, titleSeen, frames, stoppedOn}`, `{k:"emu", op:"press", keys, checkpoint: "title" | "postTitle", pass?}`, `{k:"proposal", ops, reason, force_unverified}`, `{k:"gate", verdict, reason, perOp, hash?}`. The runner merges this file into the recorded run; REPLAY re-executes from it, so every accepted patch must be reconstructible from `proposal` + `gate`.
- `refusals.json` — owned by the Pre Tool Use HOOK, never written by the server; the server only READS it (`{ "<lineno>": count }`) to pass `refusalCounts` to the gate for `force_unverified`.
- Restart rule: the runner resumes the same Kiro session in a NEW process, so the server is restarted mid-run. IF `listing.json` exists at start THEN the server loads its canonical lines (the gated state) and never re-reads `input.json`'s lines; otherwise it builds the canonical listing from `input.json`. Either way it types the canonical listing into the C64 at start (an `emu load` event).

## Tools (exact names; the agent profile trusts exactly these)
1. `c64_reload()` — no arguments (the agent can never supply program text). NEW + types the canonical listing via `loadCanonical()`; returns hash + untypeable lines with their reason.
2. `c64_run({ frames? })` — always re-types the canonical listing first (so what runs is exactly what the gate accepted), then runs it with `runListing()` (frames default 3000, max 20000). If the title predicate appears, the SERVER presses `spec.postTitle.keys` itself (runListing already does) — the agent never presses post-title keys. Returns the screen after RUN, the parsed error, titleSeen, postTitle pass/fail and both screens, and the recomputed contract heading. Clears `provisional` for every line once postTitle is "pass".
3. `c64_read_screen()` — current 40×25 screen text + parsed error (double-space `?SYNTAX  ERROR IN n` is the C64's own text).
4. `c64_press({ keys: string[] })` — each entry one key: a single printable character or "RETURN"/"SPACE". Only keys whose PETSCII code is in `spec.titlePredicate.keys` are allowed; any other key → a tool error naming the allowed keys, nothing pressed (closes a gate bypass).
5. `checksum_line({ lineno, body })` — the Gazette `:rem` sum (`computeChecksum`) plus, when that line exists, its printed checksum and whether they match (`checkLine`). Pure, no side effects.
6. `apply_patch({ ops: ({op:"replace", lineno, new_body} | {op:"renumber", lineno, new_lineno})[], reason: string, force_unverified?: boolean })` — 1–4 ops, judged atomically by `applyPatch()` from `src/gate/checksum-gate.ts` (map `op` → the gate's `type`), with `refusalCounts` read from `refusals.json`. The gate runs here too even though the Pre Tool Use hook ran it first (defence in depth: a refused patch never changes the listing). On accepted/forced: write the new canonical listing, re-type it into the C64 (`emu load` event) BEFORE returning, write listing.json, return the gate's reason + the new hash + "call c64_run next". On refused: return the gate's reason verbatim as a tool error; nothing changes. Every call appends `proposal` then `gate`. A recovered line keeps `provisional: true` until a run's postTitle passes, even if patched.

## Non-functional / failure
- zod validates every argument; a malformed call returns a tool error, never throws out of the process. Three malformed calls in a row → the server writes `{k:"error", why:"3 malformed calls"}` and every further tool returns an error saying the run is over.
- Emulator crash inside a tool → reboot the core once, re-type the canonical listing, add `{k:"emu", op:"restart"}`; a second crash → tool error "emulator crashed twice; the run ends".
- The server never writes outside `$RUN_DIR`, never reads the network, and never knows any reference/expected text of the magazine beyond `input.json`.
- Lines the C64 cannot store (`untypeableLines`: control code outside quotes, digit-leading body, nothing typeable, too long) are never typed; every load reports them to the agent as "untypeable: <reason>" so it can fix them through apply_patch.
